# Arbiter AI — remote breach containment architecture

> Goal: let Arbiter participate in an authorized live-response exercise or customer incident by deploying a small trusted edge component near the protected host, while keeping the AI brain, audit trail and operator controls in a separate Arbiter controller.
>
> This design is for systems the operator is authorized to monitor and contain. It does not turn Arbiter into a remote exploitation framework.

## Why this architecture exists

The current Arbiter runtime is strongest when it can read local endpoint telemetry directly. That works for a single Windows host, but it is not enough for a live-breach exercise where the operator may be sitting on a laptop while the protected machine lives elsewhere on a lab or company network.

The old mental model was:

```text
telemetry on this host -> Arbiter on this host -> local response
```

The new model is:

```text
protected host / network
        |
        v
Arbiter Edge Agent
  - local collectors
  - local policy enforcement
  - typed response actuators
  - local spool / priority lane
        |
        | authenticated encrypted control + telemetry channel
        v
Arbiter Controller
  - normalized event pipeline
  - guardrails
  - deterministic prefilter
  - correlation / incident graph
  - local LLM for ambiguous reasoning
  - response planner
  - operator approval
  - audit / dashboard
```

The controller can run on the operator laptop, a nearby management node, or a customer-owned server. The edge agent runs on or next to the protected asset. Raw customer telemetry stays inside the authorized environment and is sent only to the paired Arbiter controller.

## Design principles

1. **Remote access is not arbitrary shell access.** The controller never sends free-form commands generated by an LLM. The edge agent accepts a small typed action vocabulary with strict parameter validation.
2. **Guardrails remain outside the model.** Detection and containment eligibility are enforced in deterministic code before and after model reasoning.
3. **Fast containment must not wait for the LLM.** High-confidence deterministic signals get a priority path that can produce a containment proposal even if inference is slow or unavailable.
4. **Actions are scoped, reversible and time-bounded by default.** Temporary network blocks and isolation leases should expire unless explicitly renewed.
5. **The edge agent is the final policy authority for its host.** Even a compromised or mistaken controller cannot ask the agent to perform an action outside its locally configured policy.
6. **Every action is attributable.** Proposal, approval, dispatch, execution, verification, expiry and rollback are all recorded.
7. **The breakout clock is a product metric.** Arbiter should measure time from first relevant signal to detection, assessment, approval and containment.

## Deployment modes

Arbiter should support three explicit modes instead of treating every runtime as the same deployment.

### Mode A — local endpoint mode

Current behavior. Arbiter and collectors run on one machine and the actuator affects only that machine.

```text
[endpoint]
collectors -> triage -> controller logic -> local actuator
```

Use for development, a single-host SMB deployment, and offline demos.

### Mode B — remote lab / incident mode

The controller stays on the operator machine. A lightweight edge agent is installed on the authorized target using an existing administrative channel such as SSH, WinRM, RMM, image provisioning or a manual package install.

```text
[operator laptop / controller] <==== secure session ====> [target edge agent]
                                                     -> Sysmon / Defender / logs
                                                     -> local typed actuators
```

This is the preferred mode for TryHackMe-style exercises when the event rules permit installing software on the protected machine.

### Mode C — multi-host organization mode

Many edge agents connect to one or more controllers inside the customer network. Network sensors and cloud connectors feed the same incident pipeline.

```text
                    +--> edge agent: workstation-01
                    +--> edge agent: server-02
controller / brain -+--> edge agent: server-03
                    +--> Suricata / Zeek sensor
                    +--> Wazuh / cloud connectors
```

This mode requires production transport, multi-worker ingestion and per-asset authorization that are beyond the current MVP.

## New logical components

### 1. Arbiter Controller

The controller owns the security reasoning plane.

Responsibilities:

- enroll and identify edge agents;
- receive normalized telemetry and health information;
- preserve trusted provenance for agent-delivered events;
- run guardrails and deterministic prefiltering;
- correlate activity into incidents and attack paths;
- invoke the local LLM only for ambiguous reasoning;
- create response proposals from a typed action catalog;
- obtain operator approval when policy requires it;
- dispatch signed action requests;
- verify results and show rollback/expiry state;
- track breach-response timing metrics.

The controller does **not** need operating-system administrator rights on every protected machine. Those rights remain local to the edge agent service account or host service.

### 2. Arbiter Edge Agent

The edge agent is intentionally small. It is not a second AI runtime.

Responsibilities:

- collect host telemetry from approved local sources;
- normalize events or send a compact trusted envelope to the controller;
- apply local priority tagging for obvious high-value events;
- spool telemetry during short controller outages;
- enforce host-local response policy;
- execute only registered typed actions;
- return action result, verification evidence and rollback state;
- expose heartbeat, queue depth, collector health and current containment leases.

The edge agent should not contain an LLM, should not accept arbitrary code and should not expose a generic remote terminal through Arbiter.

### 3. Secure Control Plane

The controller-agent relationship needs an explicit trust protocol.

Minimum properties:

- one-time enrollment or administrator-approved pairing;
- mutually authenticated encrypted transport;
- per-agent identity and certificate/key material;
- controller identity pinning;
- replay protection for action requests;
- monotonically increasing or unique action IDs;
- short-lived action authorization tokens or signed requests;
- agent-side scope policy;
- revocation and emergency disconnect;
- no trust based only on source IP.

A future CLI may look like:

```text
arbiter agent enroll --controller <controller-address> --token <one-time-token>
arbiter agents list
arbiter agent status <agent-id>
```

A convenience deployment wrapper may automate package transfer over an **existing authorized admin channel**, for example:

```text
arbiter deploy --ssh admin@10.10.10.25
```

That command should only install/enroll the agent. It must not turn Arbiter into a scanner or attempt to discover credentials or exploit a host.

### 4. Telemetry Plane

Remote telemetry should preserve the current `SecurityEvent` contract while adding authenticated agent provenance.

Suggested envelope:

```text
agent_id
asset_id
sequence
observed_at
received_at
collector
collector_version
schema_version
event
signature
```

The controller verifies transport identity and envelope integrity before assigning trusted-agent provenance. Uploaded files and generic HTTP events must never be able to claim this trust class.

The telemetry plane needs two lanes:

```text
PRIORITY LANE
  guardrail candidates
  security-tool critical findings
  suspicious process/network correlations
  containment-result events

NORMAL LANE
  routine process / inventory / low-severity telemetry
```

This prevents an event flood from placing a confirmed high-risk signal behind thousands of routine Sysmon records.

### 5. Incident Graph / Breach State

A live breach should no longer be treated as independent alerts only. Arbiter needs a persisted incident graph.

Example:

```text
user clicks attachment
        |
        v
powershell.exe
        |
        +--> outbound C2
        |
        +--> credential access signal
                    |
                    v
               account A
                    |
                    v
              remote logon
                    |
                    v
               host B
```

Each node/edge should retain evidence IDs and confidence source:

- deterministic rule;
- trusted security-tool finding;
- correlation;
- analyst confirmation;
- model inference.

The LLM may help explain or rank a graph, but it must not invent graph edges without evidence references.

## Breach-response decision path

The new live-response path should be:

```text
telemetry
   |
   v
trusted normalization
   |
   v
hard guardrails / priority classification
   |
   +--> deterministic containment candidate --------+
   |                                                |
   v                                                |
cheap prefilter                                     |
   |                                                |
   +--> clear benign -> observation                 |
   |                                                |
   +--> clear suspicious -> incident update --------+
   |                                                |
   +--> ambiguous -> local LLM -> guardrail veto ---+
                                                    |
                                                    v
                                           response planner
                                                    |
                                                    v
                                          containment policy
                                            /      |      \
                                         auto   approve   deny
                                            \      |      /
                                                    v
                                           signed action request
                                                    |
                                                    v
                                              edge actuator
                                                    |
                                                    v
                                            verify + audit + TTL
```

### Fast path

A critical design requirement is that the deterministic path does not queue behind model inference.

Examples of signals that may enter the fast path once validated:

- Defender malware finding tied to the exact executable seen by Sysmon;
- that exact process opening a connection to a public address;
- confirmed repeated credential attack followed by successful remote login;
- trusted sensor finding plus exact endpoint/process correlation;
- an already-contained IOC reappearing on another enrolled endpoint.

The fast path may create a containment proposal immediately. Automatic execution should still depend on the local policy tier described below.

## Typed containment actuator registry

The action interface is a contract, not a shell command.

Initial action families:

| Action | Example parameters | Default policy |
|---|---|---|
| `network.block_ip` | address, direction, ttl | approval or narrowly auto-approved |
| `network.block_domain` | domain, ttl | approval |
| `process.terminate` | pid + executable identity | approval |
| `process.suspend` | pid + executable identity, ttl | approval |
| `host.isolate` | controller allowlist, ttl | approval |
| `host.release_isolation` | lease_id | operator or expiry |
| `file.quarantine` | exact path + hash | approval |
| `persistence.disable_service` | service identity, ttl | approval |
| `persistence.disable_task` | task identity, ttl | approval |
| `identity.lock_local_account` | exact local account, ttl | high-friction approval |
| `identity.revoke_session` | session identity | high-friction approval |

The first implementation should stay small. Windows firewall IP blocking already exists and should become the first registered actuator rather than being replaced.

Every action implementation should support as many of these operations as applicable:

```text
validate -> plan -> execute -> verify -> rollback -> expire
```

The action request includes the evidence IDs that justified it. The edge agent revalidates target identity immediately before execution where possible. A process action, for example, should avoid acting on a recycled PID without matching executable/start-time identity.

## Containment policy tiers

The controller and agent should share a policy model.

### Tier 0 — observe only

No protective action can execute. Useful for first deployment and event-rule uncertainty.

### Tier 1 — reversible deterministic auto-containment

Only a very small allowlist of actions may execute automatically when deterministic evidence and local policy both match.

Candidate MVP example:

- temporary block of a specific public IP tied to a verified malware-process/network correlation;
- short TTL;
- no broad subnet, wildcard or service shutdown;
- automatic rollback;
- full audit.

### Tier 2 — human-approved containment

Actions such as process termination, host isolation, service/task disablement and file quarantine require operator approval.

### Tier 3 — high-impact identity / infrastructure action

Actions affecting identity providers, multiple hosts, broad network segments or business-critical services require explicit high-friction approval and should not be auto-executed by the MVP.

The LLM can recommend an action but cannot change its policy tier.

## Host isolation design

Host isolation is one of the highest-value actions for a breakout-time exercise and should be implemented early.

The safe form is a temporary host firewall policy that blocks normal inbound/outbound traffic while preserving an explicit management path to the Arbiter controller and any required infrastructure endpoints.

Conceptually:

```text
normal traffic --------X
lateral movement ------X
C2 / exfiltration -----X

Arbiter control channel ---> allowed
required local loopback ---> allowed
explicitly configured infra -> optionally allowed
```

Important safeguards:

- the agent computes the allowlist before applying isolation;
- the controller connection must not be the only rollback mechanism;
- a host-local watchdog automatically releases isolation at lease expiry;
- an administrator can release isolation locally;
- isolation never becomes a permanent firewall rewrite;
- the agent verifies the active ruleset after execution.

## Throughput redesign for live incidents

The current single-worker/10,000-record queue is not a sufficient long-term breach-response architecture. The revised architecture separates acquisition, priority detection and expensive reasoning.

```text
collectors
   |
   +--> bounded local spool
   |
   v
normalizer
   |
   +--> priority detector --------> fast correlation/guardrails --> response candidate
   |
   +--> normal event queue -------> worker pool ------------------> ordinary triage
                                                      |
                                                      +--> LLM queue only when needed
```

Required changes:

- separate ingestion from AI inference queues;
- preserve a high-priority lane with bounded latency;
- support multiple analysis workers without double-processing;
- deduplicate by stable event identity;
- apply backpressure before raw telemetry exhausts memory/disk;
- summarize/rate-limit repetitive low-value telemetry;
- never drop containment results or high-priority findings silently;
- expose **event age at decision time**, not only model inference duration.

The goal is not to send every Sysmon event to an LLM. The goal is to ensure high-value evidence reaches deterministic correlation quickly while routine telemetry can lag safely.

## Live-breach metrics

Every incident should carry a clock beginning at the earliest retained signal that contributes to the incident.

Arbiter should record:

- **TTD — time to detect:** first relevant event -> first escalation;
- **TTA — time to assess:** first relevant event -> incident classification / containment proposal;
- **TTP — time to propose:** first relevant event -> first actionable containment recommendation;
- **TTC — time to contain:** first relevant event -> verified containment action;
- **approval delay:** proposal -> operator approval;
- **execution latency:** approval -> verified action;
- **event age:** occurrence -> analysis;
- **false containment rate;**
- **rollback rate / failed action rate;**
- **attack-path interruption rate.**

For breakout-style exercises the engineering target should be substantially below a 29-minute attacker breakout benchmark. A practical first goal is **under five minutes to the first verified meaningful containment** for attack paths Arbiter has evidence to stop.

## CLI and operator experience

The CLI should make deployment status explicit.

Illustrative commands:

```text
# controller
arbiter controller start
arbiter agents list
arbiter incidents live

# deploy through an already-authorized admin path
arbiter deploy --ssh admin@10.10.10.25

# manual enrollment on a host
arbiter agent install
arbiter agent enroll --controller 10.10.10.5:7443 --token <one-time-token>

# response posture
arbiter policy set --agent <id> --mode approve
arbiter policy set --agent <id> --mode observe

# emergency operator action through the typed API
arbiter contain isolate-host --agent <id> --ttl 10m
arbiter contain release --lease <id>
```

These are target interfaces, not a claim that the current CLI already implements them.

## Event / exercise workflow

For an authorized live exercise:

```text
1. Connect operator laptop to event/lab network.
2. Start Arbiter Controller locally.
3. Deploy or manually install Edge Agent on the assigned protected host if event rules allow it.
4. Pair agent to controller.
5. Confirm collectors and action permissions.
6. Start in Observe or Approval mode.
7. Begin exercise.
8. Watch incident graph and breakout clock.
9. Approve containment proposals as needed.
10. Export incident timeline and containment evidence after the event.
```

If the event does **not** permit installing an edge agent, Arbiter should fall back to a connector mode that consumes the event's existing SIEM/EDR telemetry. In that case containment is limited to whatever approved response API that platform exposes.

## Failure model

The breach architecture must define failures explicitly.

### Controller unavailable

- agent continues collecting to bounded local spool;
- existing containment leases still expire locally;
- no new controller-driven Tier 2/3 actions execute;
- optional Tier 1 actions may run only if they were pre-authorized by local deterministic policy.

### Agent unavailable

- controller marks telemetry stale;
- incident UI must distinguish "no new evidence" from "healthy endpoint";
- response actions fail closed rather than being reported as successful.

### LLM unavailable

- deterministic guardrails, correlation and eligible fast-path response continue;
- ambiguous events escalate for human review;
- no containment depends solely on model availability.

### Queue overload

- priority lane remains serviceable;
- ordinary telemetry may be delayed or summarized;
- UI shows event age and dropped/summarized counters;
- no claim of complete coverage is made when the priority guarantees are exceeded.

## Security boundaries

The following are non-negotiable:

- no arbitrary LLM-generated shell execution;
- no remote deployment without an existing authorized admin path or manual install;
- no trust based on an uploaded `agent_id` field;
- no action without target scope validation;
- no broad firewall wildcard generated from model text;
- no silent permanent containment;
- no controller-initiated credential discovery;
- no automatic expansion from one compromised host to unrelated hosts;
- every agent can be revoked independently;
- every action is immutable in audit once dispatched.

## Implementation phases

### Phase 1 — remote edge foundation

- introduce controller/agent identities;
- agent enrollment and heartbeat;
- authenticated encrypted transport;
- remote `SecurityEvent` delivery with trusted provenance;
- per-agent status in dashboard;
- bounded local spool;
- preserve current local runtime as Mode A.

**Exit criterion:** a remote Windows/Linux lab host can stream live telemetry into the existing Arbiter incident pipeline without using a generic shell channel.

### Phase 2 — response RPC and policy engine

- typed action registry;
- convert current Windows IP block into an action provider;
- signed action requests/results;
- approval states;
- TTL lease model and local watchdog;
- verification and rollback records.

**Exit criterion:** controller can safely request and verify a temporary IP block on a paired lab endpoint.

### Phase 3 — first real containment pack

Prioritize:

1. host isolation;
2. process terminate/suspend;
3. file quarantine;
4. service/task disable;
5. Linux firewall/process equivalents.

**Exit criterion:** a multi-stage lab attack can be interrupted through at least two independent containment mechanisms.

### Phase 4 — incident graph and breakout clock

- persisted incident state machine;
- attack-path edges with evidence references;
- containment objective tracking;
- TTD/TTA/TTP/TTC metrics;
- exercise export report.

**Exit criterion:** Arbiter can show what happened, why it acted, when it acted, and which attack path was interrupted.

### Phase 5 — throughput / multi-host scale

- priority queue and independent fast path;
- multi-worker analysis;
- deduplication/leases;
- network sensor integration;
- multi-agent policy and fleet health;
- identity/cloud response providers.

**Exit criterion:** sustained telemetry load cannot starve deterministic high-priority containment under the documented capacity target.

## Relationship to Red-AI

Red-AI and Arbiter remain separate trust domains.

```text
Red-AI = authorized adversary / attack planner
Arbiter = defender / detection / containment
```

They may share a lab to create measurable attack/defense exercises, but Red-AI never receives Arbiter actuator credentials and Arbiter never delegates containment decisions to Red-AI.

A useful future test harness is:

```text
Red-AI attacks lab target
        |
        v
Edge Agent observes target
        |
        v
Arbiter Controller detects/correlates
        |
        v
Arbiter contains
        |
        v
score: time-to-detect / time-to-contain / attack path stopped
```

That turns the ecosystem into a repeatable security benchmark instead of a scripted demo.

## Immediate architecture decision

The next major Arbiter capability should be **Remote Edge + Containment**, not deeper dashboard polish and not arbitrary remote scanning.

The first usable milestone is intentionally narrow:

```text
Controller on operator laptop
        <->
paired edge agent on authorized Windows target
        -> Sysmon + Defender + Windows logs
        -> priority telemetry channel
        <- typed Windows firewall containment request
        <- host-isolation request
        -> verified result + TTL rollback
```

Once this works reliably, the same contracts can support Linux agents, Wazuh/EDR connectors, network sensors and customer fleet deployments without changing the core AI/guardrail design.
