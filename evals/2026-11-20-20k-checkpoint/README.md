# Arbiter AI evaluation progress and development roadmap

**20,002 saved decisions from AIT-ADS, compared with the first published 26,002-record checkpoint. Prepared November 20, 2026. Local review copy.**

Arbiter AI's latest evaluation shows progress in both alert handling and the role of its second brain. Across **20,002 saved decisions**, L2 quieted **496 of the 767 unannotated warnings raised by L1—a 64.67% reduction in that alert list**. The first published checkpoint recorded a 0.35% L2 reduction. Gemma now investigates escalations and makes decisions that materially reduce the number of warnings left for review.

The complete L1/L2 pipeline retained **17,304 of 17,305 attack-labelled records: 99.994% attack retention**, while quieting **89.95% of unannotated records**. This checkpoint adds attack-labelled activity to the evaluation; the first published run contained none. One wrongly suppressed account/session record gives the next development cycle a specific reasoning gap to address.

The checkpoint delivered **20,002 saved decisions in 7 hours, 58 minutes, 9 seconds**, reaching **76.93% of the planned 26,000 records**. All 17,305 attack-labelled records in the selection have completed decisions. The remaining 5,998 unannotated records include 57 already admitted but unfinished. Repeated evidence-validation errors triggered the configured stop; every completed result was preserved for analysis. The plan below turns those findings into the next reliability and speed improvements.

## What the public dataset contains

The source is the **AIT Alert Data Set, version 1**, by Max Landauer, Florian Skopik and Markus Wurzenberger at the AIT Austrian Institute of Technology. It contains warnings generated by security tools during simulated normal activity and staged multi-step attacks across eight networks. Examples include login events, software activity, web requests, scanning, password attacks and privileged commands. [Dataset and attribution](https://zenodo.org/records/8263181), [research paper](https://doi.org/10.1145/3675741.3675748), [publisher's scripts](https://github.com/ait-aecid/alert-data-set).

Arbiter's adapter supports 2,600,263 Wazuh/Suricata records in the full archive and excludes 55,558 unsupported AMiner records. This evaluation uses the Fox scenario. Completed records span **January 18, 2022, 12:37:00–17:06:09 UTC**, approximately **4 hours 29 minutes of recorded activity**. The planned 26K selection extends further, to January 19 at 10:13:35 UTC.

The publisher marks attack records with phase labels. A record without an attack label is called **unannotated** here. It may be ordinary activity, a noisy detector warning or activity the annotation does not resolve. Missing labels do not independently prove that it is safe. The models never received the scoring labels.

For every 767 unannotated warnings L1 raised in this checkpoint, L2 removed 496 from the final alert list: **496 fewer warnings requiring review**. The wrongly suppressed attack is accounted for separately in the table and the account/session analysis below.

These retained warnings are requests for investigation, rather than claims that an attack has been confirmed.

The **98.64% agreement with publisher labels** is calculated as `(17,304 retained attack records + 2,426 quieted unannotated records) / 20,002`.

The observed share of unannotated records quieted rose from **57.52% to 89.95%—an increase of 32.43 percentage points**. Expressed per 1,000 unannotated records, the recorded retained-warning rate moved from about **425 to 100**, a **76.34% lower rate**.

Gemma was exercised much more extensively, with **759 review attempts versus 43—17.65 times as many**. The observed overall replay rate rose from **29.84 to 41.83 saved records per minute**, a **40.20% increase in the recorded rate**. The per-path timings below show where the remaining L2 bottleneck sits. Completing the full checkpoint without repeated evidence errors is the next reliability milestone.

## Which layers did the work

The pipeline uses Qwen3.5:4b as L1 and Gemma4:12b as L2. The model weights match the first published run. Both models run locally through Ollama; a compatible local model can replace either backend. This replay started no live collectors, response executor or cloud calls.

Changes included before this run were:

- **Corrected L2 routing:** unresolved eligible Qwen escalations reach Gemma instead of being retained by a missing-context rule before the model sees them.
- **Stronger evidence checks:** recognize more native web-attack warning formats and retain HTTP anomalies when the request is missing. Previous model decisions are described as unverified history, not proof that an activity is benign.
- **Better host identification:** prefer the hostname recorded in the original event over a generic collector name, while preserving original identities and network endpoints.
- **Five bounded workers:** intake, L1, L2 pre-filter, L2 and final checks can work on different records, with queues limiting unfinished work.
- **Less unnecessary model work:** valid retain-only Gemma decisions skip a checking call that cannot suppress them. Every proposed suppression still requires its separate check.
- **Safer failure handling:** a single failed review retains the alert and allows progress; repeated failures stop deliberately. Saved results and the failing stage are preserved.

| Stage | Job in everyday language | Observed result |
|---|---|---|
| Gateway | Normalize the incoming record and preserve its evidence | Separate evaluation databases; original source timestamps and raw fields retained |
| L1 rules and Qwen | Handle clear cases quickly; assess uncertain records | Safety rules retained 17,300 attack records; 787 Qwen calls were attempted |
| L2 pre-filter | Quiet independently supported routine escalations, or pass them to Gemma | **Zero pre-filter suppressions and zero learned-pattern hits** |
| Gemma L2 | Reconsider eligible Qwen escalations and propose keep or suppress | 747 valid reviews; 496 unannotated records quieted and one attack record wrongly quieted |
| Final checks | Reject unsupported evidence, low-confidence suppression and protected risk cases | 11 invalid Gemma outputs rejected; 24 otherwise completed suppression proposals blocked |

Of those 24 completed suppression proposals, **18 failed the 90% confidence requirement** and **six met explicit risk vetoes**: four missing-HTTP-request cases and two privileged-session cases. The 11 invalid-output rejections are separate from these 24 decisions.

The routing correction lets Gemma investigate escalations that the earlier missing-context rule retained before model review. The next step is to make the L2 pre-filter and scoped learned memory contribute as well: both recorded **zero shortcut hits** in this checkpoint, giving the optimization work a clear starting point.

## Strengthening account and session decisions

**Record 17,856** is a publisher-labelled `attacker_change_user` record. The source shows a system-managed session opening for an account, with `uid=0` recorded as the initiating identity. It is a normal-looking log line within an attacker-labelled phase; the isolated record does not itself show the whole attack sequence.

Qwen escalated it. Gemma suppressed it at **90% confidence**, explaining that the session had no accompanying failed attempts or evidence of privilege escalation. Gemma's separate checking call accepted that explanation, and the final checks allowed suppression.

**The reasoning failure:** a lack of failed logins or observed escalation did not establish that this session was authorized. The model needed a positively supported ordinary explanation or better surrounding account/session context. At the same time, `uid=0` in a system-managed session alone is not proof of an attack, so a broad rule against every such session would create unnecessary warnings.

This case identifies a gap in **Gemma's decision, its checking call and the final suppression policy**. Gemma's checking call accepted **all 521 completed recommendations it checked**, including this miss. I plan to strengthen the evidence required for authentication-related suppression and test the checker against deliberately plausible but unsupported explanations.

## Reliability findings and planned fixes

There were **13 processing failures, or 0.065% of saved records**. Every affected record stayed flagged. They are operational/validation failures, separate from the one wrongly suppressed attack.

| Failure | Count | Records | What happened |
|---|---:|---|---|
| Unsupported destination-port claim | 1 | 17,463 | Gemma's cited evidence did not pass the exact-value check |
| Unsupported username claim | 2 | 17,703; 17,705 | Same evidence-validation problem |
| Unsupported alert-signature claim | 1 | 18,032 | Same evidence-validation problem |
| Unsupported failed-login-count claim | 7 | 18,086; 18,161; 18,165; 19,730–19,733 | A claimed count for the same peer within five minutes failed validation |
| Gemma server error | 1 | 17,784 | Ollama returned HTTP 500; its log records CUDA out of memory |
| Qwen server error | 1 | 20,059 | Ollama returned HTTP 500; its log records CUDA out of memory |

The configured stop activated after **three consecutive model failures** during the repeated failed-login-count errors; one more failed L2 review completed during shutdown. All saved outcomes, including failures, remain preserved. The next update will target these repeated evidence-format errors while keeping the rule that failed reviews leave alerts visible.

The output format permits Gemma to name an evidence field and value, while the validator requires an exact match to a supplied fact. A valid-looking answer can therefore fail if its field, value or type does not match. Error logs identify the rejected field but do not preserve the rejected value, limiting a more precise diagnosis. A future compact decision should reference validated assertion IDs rather than ask the model to retype facts freely.

## Speed and queue delay

The five workers ran concurrently, but Gemma still processed one review at a time. Its two upstream queues filled with 32 waiting items each. A five-worker pipeline does not imply five GPUs or five simultaneous Gemma reviews.

| New-run measurement | Average | 95th percentile | Maximum |
|---|---:|---:|---:|
| Rule-handled record, ingestion to final decision | 0.20s | 0.19s | 27.01s |
| Qwen model call | 10.68s | 13.23s | 15.58s |
| Gemma main assessment call | 31.84s | 36.85s | 75.70s |
| Gemma checking call, when required | 3.15s | 3.75s | 7.50s |
| Gemma model-call time summed per reviewed record | 34.00s | 39.42s | 82.54s |
| Gemma-routed record, ingestion to final decision including waiting | **36m 09s** | **40m 40s** | **40m 59.55s** |

The 95th percentile means 95% of records on that path finished within the stated time. A few long delays can make the average larger than the 95th percentile on the fast rule path. The overall median, 0.157 seconds, hides the slow model path because only 3.79% of saved records went through Gemma. It should not be advertised as typical L2 latency.

Gemma spent about **3.95 seconds reading** and **27.26 seconds generating** its main answer, which averaged **590 output tokens**, or pieces of text. Report generation was the largest part of its model work. Keeping an alert visible no longer triggers a redundant checking call: **226 valid retain-only reviews skipped it**. Proposed suppressions still need the check. Loading the model averaged only about 0.07 seconds, so repeated model loading was not the main average delay.

The machine used an Intel i7-13700F, 31.8 GiB system RAM and an RTX 4060 Ti with about 16 GiB dedicated VRAM, driver 621.24. Qwen and Gemma shared the GPU. The dashboard was terminated and its automatic restart disabled. Other desktop applications still shared system RAM and storage. Read-only diagnostics during the run found little spare physical RAM, heavy Windows memory compression, substantial pagefile use and disk-activity spikes. Those snapshots show resource pressure; they do not identify the exact memory available at each failure.

The published baseline's per-record times excluded pre-processing queue residence. New ingestion-to-final times include actual queue waiting, so those latency columns must not be treated as equivalent. The earlier 104-minute delay discussed elsewhere was a simulation of the old run; the roughly 41-minute maximum here was observed in this replay. No commercial product was tested on matching records, hardware and quality requirements.

## My plan for the next update

My next development cycle will focus on faster evidence-backed decisions, useful learned filtering and more reliable operation under sustained load. I will keep the immediate alert decision separate from the longer explanation, then test the results against the saved failures and additional attack examples.

| Priority | Proposed change | Purpose and acceptance check |
|---|---|---|
| 1 | Repair evidence references and session suppression | Choose assertion IDs from the actual packet; distinguish missing context from verified ordinary behavior. Reproduce each rejected-field failure class and record 17,856, then test ordinary lookalikes and unseen account/session attacks. Do not hard-code a dataset account or suppress an entire host. |
| 2 | Separate the urgent decision from the long report | Keep decision, confidence, exact evidence and a short reason in the immediate path, with suppression checks still required. Generate the longer investigation narrative on request or when the GPU is otherwise free. |
| 3 | Make L2 pre-filtering and learning useful | Measure why current shortcuts produce zero hits. Add only scoped, evidence-backed routine patterns, with expiry, revocation and attack-lookalike tests; a suppression percentage is not a safety target. |
| 4 | Bound memory and reduce storage overhead | Measure per-model caches and GPU headroom, test smaller processing batches and a deliberate CPU/GPU split if necessary, and reduce unnecessary full-file rechecks while preserving frozen-input integrity. Keep concurrent Qwen/Gemma as requested. |
| 5 | Run a matched replay and then a separate endurance test | Freeze identical inputs and labels outside prompts; start fresh memory and compare each deciding layer, missed attacks, review volume, queue delay, GPU/RAM and disk use. Then evaluate a separate attack-rich window and the planned ten-hour capacity run. |

For a shorter 200–300-token decision, my planning target is **18–23 seconds of model-review work per L2 record**, versus the observed 34 seconds: approximately **32–47% less model-review time** if generation speed holds. I will measure that target in the next evaluation, alongside queue delay, alert quality and memory use.

The longer report must not compete with urgent reviews on the same saturated GPU. Shorter answers must still carry enough evidence to justify the decision; simply truncating today's output would create more invalid replies. The authentication miss, identical-record regressions and ordinary lookalikes must pass before a new speed result is presented as an improvement.

AWS connector support is already optional in the source and was tested with mocked SDK sessions in a separate environment. It does not accelerate local models. This benchmark made no AWS calls and did not upgrade the installed dashboard. Decision/report separation and the new proposals above were not part of these measured results.
